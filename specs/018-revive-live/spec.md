# Spec 018：实时数据恢复与离线可用

## 背景

2026-10 起寿司郎小程序把实时排队接口从 `crm-cn-prd.sushiro.com.cn/wechat/api/2.0`（本项目用一个写死的公共 token）换到 `sapi.sushiro.com.cn/gateway/wechat/api/2.0`。新网关要求绑定会员账号的 Bearer token（JWT，约 1 小时到期）和 `x-app-client`、`x-app-code`、`User-Agent`、`Referer`、`Content-Type` 等请求头；token 由小程序用微信 `js_code` 加签名换取，只有微信客户端能续期。旧地址匿名请求返回 401/403。

公开资料（第三方项目 Serenin0x/sushiro-queue-predictor 的实测记录，非官方）显示：新网关 `getStoreById?storeId=N` 直接返回与旧接口相同字段的门店 JSON（无外层信封），`stores?latitude=1&longitude=1&numresults=10000` 直接返回门店数组；缺 `authorization` 返回 401，缺 UA/Referer/Content-Type 曾返回 400。

结果：应用的实时叫号、开始记录 / 后台记录、叫号提醒、取号前的状态展示、门店选择全部失效；服务器采集器停在 2026-09-06。

## 目标

让应用在两种状态下都有用：

1. **不连接也能用**：门店可选；“想几点吃”按历史规律给取号时间；“我拿了 N 号，小程序里现在叫到 M 号”给出大概几点叫到；可以手动记一笔叫号。所有离线结果标明“历史参考（截至 2026-09-06）”。
2. **连接后（1 小时内）恢复实时**：用户用自己的小程序请求授权一次（手机或电脑抓包，或粘贴抓包里的一条请求），应用在 token 有效期内恢复实时叫号、记录和提醒；到期前提示重新打开小程序刷新一下再连接。手机经本应用代理浏览小程序时，看到的门店数据也会被顺手记下。

## 非目标

- 不做无人值守续期：不生成 `js_code`、不模拟微信、不使用从小程序包里提取的签名密钥。
- 不把会员 token 交给独立后台进程或服务器；独立后台记录在没有连接时停止并说明原因。
- 不恢复服务器采集；`data` 分支作为截至 2026-09-06 的历史存档继续发布。
- 不改变取号的安全规则：一次确认、一次提交、不自动重试。

## 用户可见行为

| 场景 | 行为 |
|---|---|
| 没连接，打开排队页 | 显示“实时叫号需要连接（约 1 小时有效）”，给出连接入口；同时可输入“小程序里现在叫到几号”和“我的号码”，得到预计叫到时间（历史叫号速度推算，标明是参考） |
| 没连接，想几点吃 | 用本机记录或内置历史的等待规律给取号时间，标明数据截止日期 |
| 没连接，选门店 | 门店列表来自内置历史和本机记录，按区域搜索可用 |
| 连接后 | 实时叫号、在等桌数、官方预估恢复；开着应用时按设定间隔记录；叫号提醒可用；剩余时间显示在设置里 |
| 连接快到期 / 已到期 | 停止实时请求，不重试；提示“打开小程序刷新一下，再连接一次” |
| 独立后台记录（关窗后） | 不使用会员 token；状态显示“需要打开应用并连接实时数据”，不再每 30 秒撞已失效的接口 |
| 手动记一笔 | 只写入本机观测（用于叫到时间校准和提醒），不混入“我的记录”等待曲线 |
| 取号 | 仍需账号凭证；查询现有号码失败时拒绝提交，提示去小程序里取号，避免重复取号 |

## 验收

- 无网络、无连接时：门店可选、想几点吃有结果、输入叫号得到时间区间，界面没有“HTTP 403”或 VPN 字样。
- 粘贴一条网关 `getStoreById` 请求（curl / 原始请求头 / HAR）后，实时面板走新网关；token 过期后零请求并提示重新连接。
- 采集器在认证类失败后不再每 30 秒重试；状态文案准确。
- 离线叫到时间推算在内置历史回测中 1 小时提前量平均误差 ≤ 20 分钟。
- 全部测试通过，新增行为均有测试。
