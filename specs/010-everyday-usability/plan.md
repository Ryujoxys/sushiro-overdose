# 实施方案

## 模块

- `webui/index.html`：首页次要入口、导航、取号表单和预测/设置文案。
- `webui/app.css`：主操作与弹窗层级、响应式表单、焦点可见性和触控面积。
- `webui/quick_flow.js`：可编辑确认、认证前后内存草稿、本机分析简化状态。
- `webui/app.js`：选店错误重试和焦点管理、公开排队请求序号、少量页面衔接。

## 边界

复用既有 REST 协议，不改后端数据结构。人数草稿仅存页面内存，认证中断后清除；明确确认后才 POST 取号。门店搜索和预览只有 GET。后台采集的选择、启用、暂停保持独立操作。

代码检查发现 `queue_baseline.go` 在配置缺失或损坏时默认开启，与可选启用交互不一致。本轮唯一的后端调整是默认关闭持续采集，保留已保存的显式开关，并加回归测试。实时页面另需区分营业状态与线上取号状态，不能因为门店营业就宣称可取号。

## 交互

1. 选择一家门店，核对人数。未认证时说明还需获取本人凭证。
2. 获取完成后返回同一门店和人数，再明确确认取号。
3. 提交中禁用重复动作，成功突出号码，失败保留只读查询入口。
4. 对话框打开时锁定背景滚动并圈定 Tab 焦点，退出恢复原焦点；搜索请求按会话序号丢弃迟到结果。

## 验证

运行前端 VM 行为测试与静态嵌入检查，覆盖人数编辑、无效输入、取消、认证保留、重复提交、门店加载重试、迟到结果和公开服务选择步骤。运行 `go test ./...`、`go vet ./...`、JavaScript 语法检查与 `git diff --check`。不启动 Web 服务或执行任何真实业务操作。
