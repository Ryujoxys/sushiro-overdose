# 寿司郎排队查询

数据来自 `https://raw.githubusercontent.com/Ryujoxys/sushiro-overdose/data/`（每天导出一次，格式见 `docs/public-data.md`）。拿不到时脚本自动改用仓库里的内置历史包。实时数据只来自用户本机运行的 sushiro 应用（`127.0.0.1:39871`），脚本不直接请求寿司郎接口。

## 用法

```bash
Q="python3 .claude/skills/sushiro-queue/scripts/sushiro_queue.py"
$Q status                                   # 数据范围、截止时间、采集是否正常 —— 每次先看
$Q stores 太阳宫                             # 按名称/城市/区域/地址找门店 ID
$Q pattern 3006 --date 2026-10-24 --from 17:00 --to 21:00   # 那天各半小时：通常要等 / 八成日子不超过 / 通常叫到 / 常见范围
$Q pattern 3006 --type weekend --recent 30  # 指定日期类型、只用最近 30 天
$Q plan 3006 --eat 19:00 --travel 20 --date 2026-10-24      # 想几点吃 → 几点取号
$Q eta 3006 --ticket 1350 --called 1180 --called-at 18:20   # 手里的号几点叫到：填小程序里现在叫到几号，按以往叫号速度推算（最准）
$Q eta 3006 --ticket 1350 --date 2026-10-24 --after 17:00   # 不知道当前号码时，只看历史
$Q live 3006                                # 实时（本机应用），否则线上最后一次采集
$Q day 3006 2026-09-05                      # 某天的逐半小时记录
```

所有命令可加 `--json`。门店参数可以是 ID 或唯一的名称片段。`--date` 默认今天；脚本按那天每个时段自己的日期类型取规律（节假日表优先；周五 16:30 起、周六、周日 22:00 前算周末）。

## 回答方式

1. 先跑 `status`。回答里说清数据截止到哪天、用了多少天的记录。截止很久或采集一直失败时直说“这是历史规律，不是现在的情况”。
2. 给区间，不给单点承诺：等待用“通常要等 X 分钟，八成日子不超过 Y 分钟”，叫号用“通常叫到 N，常见范围 A–B”。`180+` 是官方显示上限 3 小时，表示可能更久。天数少于 3 天的时段标“记录少，仅供参考”。
3. 取号方案：`plan` 的建议区间是“最贴近目标的取号时刻”到“八成日子仍不会迟到的最晚取号时刻”。等待到上限时提醒宁可更早。用户说了路上时间就传 `--travel`。
4. 手里有号：先问用户“小程序里现在叫到几号”，用 `eta --called` 推算（回测提前 1 小时平均误差约 20 分钟）；不知道当前号码时，`eta` 只给历史上快的日子（约两成）、一般（一半日子）、慢的日子（八成日子之前）叫到的时间，误差大得多。叫号是号码不是人数，不同日子起点不同、会跳号，只能比较同一时段。本机应用开着时它会补充“现在叫到几号、还差多少”。
5. 当天决策优先看 `live`；只有线上最后一次采集时，说明那是几点的数据。
6. 不编数据：没有记录的时段说没有，不用相邻时段或别的店顶替。

## 边界

- 只读。脚本和本技能都不会取号、取消或改设置；用户要取号时，引导用户在 sushiro 应用里手动确认，应用只取一次、不自动重试。
- 不需要也不要索取任何账号、手机号、token。数据库 key 只给仓库维护者的导出工作流用。
- 数据只有门店公开状态，不能推断个人信息。

## 数据从哪来

维护者服务器上的采集器（`collector/`）每 15 分钟读寿司郎公开门店接口写入 Turso；`.github/workflows/public-data.yml` 用只读 token 每天导出到 `data` 分支。采集器被接口拒绝时数据会停在截止时间，`status` 会显示。目前（2026-10）寿司郎小程序改用新网关和约 1 小时的会员 token：服务器采集器停在 2026-09-06；本机应用在用户连接后（设置 → 实时数据）才有实时数据，`live` 取不到时直说没有实时数据，并请用户说出小程序里现在叫到几号，用 `eta --called` 推算。
