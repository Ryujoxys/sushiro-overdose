# 产品改造调研与方向草案

调研日期：2026-09-17。状态：待讨论，不是已批准的实现规格。

## 结论

这次应该重做信息架构和任务流程，而不只是调整颜色、间距或折叠更多面板。

建议采用一个应用、两个独立工作区：默认的「排队助手」和按需进入的「本地分析」。按用户此刻的任务分流，不给人贴「普通用户／高级用户」标签，也不增加首次使用问卷。用户可以自由切换，应用记住最后使用的工作区。

排队助手负责选店、按需认证、明确确认取号、跟进当前号码及未来预约。本地分析负责公开数据记录、门店规律与个人模型。二者共享版本化本地数据，但不共享一张堆满功能的首页，也不要求分析用户先认证。

这是一项设计建议，不是竞品已证明适合我们用户的结论。需要用原型验证。

- 参考官方产品介绍、帮助文档和官方界面展示，不以设计展示网站的静态概念图代替真实产品。
- 实际查看当前应用的首页、选店页、预测页与本地分析入口，保存了本轮截图。
- 当前截图对应已有账号数据、显示完整功能导航的窄窗口状态，不能代表所有新用户或简化模式。
- 对照前端入口代码核对模式切换、页面职责和号码传递方式；本轮没有修改应用代码。
- 参考产品没有登录实测，属于公开资料研究，不是对其完整产品的可用性审计。
- 未执行取号、预约、取消、开启采集或系统授权；也未改动用户当前订单。

## 值得学习的产品

### 任务分层

**Things** 的价值不在白底和圆角，而在控制什么事情此刻值得注意。官方文档把 Today、Upcoming、Anytime、Someday 按可行动时间区分；任务的标签、日期等附加信息按需展开。[默认列表说明](https://culturedcode.com/things/support/articles/4001304/) · [官方界面与交互展示](https://culturedcode.com/things/features/)

| 观察 | 我们可以借鉴 | 不照搬 |
| --- | --- | --- |
| 当前任务与未来任务有明确边界 | 今天取号与未来预约分开，但同属排队助手 | 不复制待办软件的全部列表分类 |
| 任务正文比附加字段更重要 | 先选门店、人数；其他偏好在需要时展开 | 不让「简约」变成所有功能都藏起来 |
| 用文字层级和分组组织信息 | 减少卡片套卡片和解释性标签 | 不照搬其颜色或旧版系统控件 |

参考图来自其官方经典设计介绍，不把该图当作 2026 年最新版本的逐像素规格。

### 进行中状态

**Citymapper** 的 GO 把已选择的行程拆成阶段，突出当下相关的下一步。其官方锁屏导航介绍也延续了持续跟进当前行程的思路。[GO 介绍](https://citymapper.com/news/597/go-your-personal-trip-assistant) · [锁屏导航介绍](https://www2.citymapper.com/news/2553/citymapper-introduces-ios-lock-screen-navigation)

| 观察 | 我们可以借鉴 | 不照搬 |
| --- | --- | --- |
| 选路线和正在赶路是两种界面重点 | 取号前看门店，取号后看手中的号 | 不持续展示完整功能菜单和新手流程 |
| 当前阶段决定下一步信息 | 等待、接近叫号、需要核对，各给一个明确动作 | 不复制地图作为主要视觉，也不把预测当官方事实 |

GO 的早期介绍只作为经典交互案例，不声称其配图代表当前完整界面。

### 当前与历史

**Flighty** 的官方演示按出发前、在机场、落地后展示行程信息；历史统计则有独立的 Passport 入口。这种「关注眼前的行程，想回顾时再看统计」的结构最接近我们的需求。[官方产品展示](https://flighty.com/) · [历史统计入口说明](https://flighty.com/help/passport)

| 观察 | 我们可以借鉴 | 不照搬 |
| --- | --- | --- |
| 当前行程的关键时间和状态突出 | 门店、号码、当前叫号、预计等待形成主卡 | 不把原始接口指标全部塞进号码卡 |
| 历史统计有独立去处 | 「本地分析」成为明确入口，不挂在取号页尾部 | 不复制其社交分享与云同步方案 |
| 展示有意义的变化与事件 | 提醒围绕本次排队，用户选择需要的提醒 | 不模仿其预测能力或准确率宣传 |

### 安静记录

**ActivityWatch** 的参考价值主要是后台服务体验，而不是视觉样式：托盘启动服务和记录组件，需要时再打开本地网页查看数据。[启动与使用说明](https://docs.activitywatch.net/en/latest/getting-started.html)

| 观察 | 我们可以借鉴 | 不照搬 |
| --- | --- | --- |
| 后台记录和前台查看分离 | 用户开启记录后不必保持分析页打开 | 不照搬其较技术化的模块和术语 |
| 本地服务有独立生命周期 | 清楚展示记录中、暂停、错误和最后成功时间 | 不默认启用，不把记录与自动取号绑定 |

**组合建议：Things 的信息层级，Citymapper 的阶段推进，Flighty 的当前／历史分离，ActivityWatch 的后台记录方式。**

## 当前界面的问题

以下是本轮页面观察与代码核对，不是用户研究的发生频率统计。

| 步骤 | 观察与健康度 | 影响 | 建议 |
| --- | --- | --- | --- |
| 1. 首页 | 主要号码可见，但任务焦点混乱。已有号码下方仍有「你现在是哪种情况」、准备清单和重复快捷入口 | 用户需要重复判断从哪里继续；取消操作在主卡上也过于突出 | 首页由当前任务状态决定内容；已有号时专注排队进度，取消保留在明确的次级操作中 |
| 2. 选店 | 可以找到门店，但信息优先级偏低效。首屏先出现解释、刷新、两类选择、门店标签、默认偏好及待收集图表 | 选中门店后仍要向下找真正的取号按钮 | 门店名称、可取号状态、官方等待参考和主动作优先；研究指标移出主流程 |
| 3. 预测 | 可用入口存在，但与当前号码的衔接依赖入口。通过导航进入时呈现手填号码和参考曲线 | 同一次用餐被拆成多个工具，用户要自己传递上下文 | 预测成为当前号码的详情；仅外部取得的号码需要手动添加 |
| 4. 本地分析 | 有独立记录能力，但入口藏在预测页的折叠区域 | 只想长期记录的人需要先理解一条不相关的排队流程 | 提供独立工作区，记录门店与本次取号门店分开管理 |

`openTicketForecast()` 可以带入号码，而顶栏进入预测页的路径独立，不能据此说所有入口都丢号码。问题是入口一致性和任务连续性。相关代码：`internal/app/webui/app.js` 中的 `go()`、`openTicketForecast()`、`applyUIMode()`，以及 `internal/app/webui/index.html` 中的主页与预测区块。

还有三个跨页面问题：

- 「通行证、只读、会执行、单据、采集、模型」混合了技术状态和用户目标，应翻译成此刻需要理解的普通表达。
- 未开启可选功能被展示为准备清单中的警告，会让人以为正常使用必须把所有功能都配置一遍。
- 同一次任务的门店、人数、凭证和号码需要一个明确的上下文，而不是让每张页面独立维护一套选择。

## 建议的信息架构

| 层级 | 入口 | 负责什么 | 不负责什么 |
| --- | --- | --- | --- |
| 工作区 | 排队助手 | 今天取号、当前号码、未来预约 | 历史模型、采集运行参数 |
| 工作区 | 本地分析 | 记录门店、历史规律、个人模型、采集状态 | 登录门槛、取号或预约计划 |
| 次级入口 | 设置与帮助 | 账号连接、通知偏好、数据管理、必要时的诊断 | 产品首页、常规使用的前置检查清单 |

「排队助手」内部保留今天、未来预约、我的记录三个明确去处。有进行中的号码时，今天页直接呈现该号码；没有号码时，显示常用门店和门店搜索。不是额外再做一张总览首页。

「本地分析」内部以门店和历史为中心：先选需要记录的店，再明确开启记录；回访时先看有意义的结论和数据覆盖程度。登录自启动、采样间隔、存储位置属于运行设置，不与结论同级。

不是拆成两个安装包、两套账号或两套数据库。一个本地应用保留统一数据协议即可。用户可以长期只用其中一个工作区。

## 核心流程

### 今天取号

1. 从常用门店或搜索结果选一家店，直接看到营业与线上取号状态。
2. 核对人数和桌型。没有可用本人凭证时，在此处进入认证，不要求先去设置页。
3. 认证返回后保留门店和人数，展示最终确认。认证成功绝不自动提交。
4. 成功后进入当前号码，不返回功能总览。提醒为可跳过的后续动作。

### 已有号码

1. 本应用已知的有效号码直接展示，不让用户再填写。
2. 在小程序或现场取得的号码可以手动添加，明确其来源以及是否经过官方核对。
3. 主视图只回答：我的号是多少、目前知道什么、等待估计是否可信、下一步做什么。
4. 过号、未知状态和查询失败分别呈现；不能用「查询不到」推断已取消或已就餐。

### 未来预约

1. 选择门店、日期和可用时段。
2. 必要时认证，明确确认后预约。
3. 定时预约等自动计划另设清晰入口，执行时间、目标和停止方式始终可见。

未来预约号不进入当天叫号预测，不再共用模糊的「单据」操作。

### 本地分析

1. 选择要长期记录的门店。这份选择不被临时取号门店覆盖。
2. 明确点击开始记录，不需要寿司郎认证，也不自动启用开机启动。
3. 展示记录状态、最后成功时间、样本覆盖和何时能提供有用结果。
4. 有足够数据时呈现门店时段规律；没有足够数据时明确说暂不能判断，不用空图表或虚假精确数字填满页面。

暂停记录和删除已有数据是两件事，不能复用一个按钮或产生隐式清除。

## 认证与提醒

认证入口建议叫「连接寿司郎账号」或「完成本人认证」，不用让用户先理解「通行证」。但它不是官方 OAuth 登录，不能包装成不存在的微信一键授权。

认证过程中必须用普通语言说明会读取本人哪些信息、保存在哪里、为何需要证书和代理、如何停止及恢复。按设备提供推荐方式，其他方式放在明确的次级入口中。默认页面不展示八个技术字段，失败时才展开必要的排障信息。

提醒在用户有号且需要提醒时再提出。正常未配置状态不全局报警；只有用户已经启用了提醒却无法送达时，才提示需要处理。系统通知与飞书等外部推送应分层，后者属于可选渠道配置。

## 视觉方向

保留寿司郎的红、白和清晰中文排版，不转成通用深色数据后台。

- 红色集中用于一个主动作、选中状态和品牌，不用大面积红色解释卡争抢注意力。
- 核心信息以文字和数字建立层级，减少阴影、套娃卡片、重复胶囊标签和装饰性图案。
- 当前号码可以像一张简洁票据，但不要同时承载完整分析报表。
- 桌面采用清晰的主列表与详情；窄窗口采用单列任务流，主动作不被大量辅助信息挤出首屏。
- 空状态说清「现在能做什么」，例如「还没有开始记录」，而不是铺开多个「待收集／未配置」。

动画仅用于让人理解状态变化，例如确认完成后进入号码页；不通过动画延迟关键操作或掩盖加载。

## 保留与移除

| 保留 | 调整方式 |
| --- | --- |
| 显式确认、只读验证、重复提交保护 | 作为交互底线保留，不以「减少点击」为由删掉 |
| 现有公开队列客户端、本地数据协议和独立采集进程 | 尽量复用，不为了换界面重写已验证的后端 |
| 自动预约、导入、诊断、推送渠道等能力 | 有独立、明确的去处，不统一暴露在首页 |
| 未来预约 | 保持可发现性，不把它误当成只能隐藏的技术功能 |

| 从主流程移走或取消 | 原因 |
| --- | --- |
| 总览首页、重复的新手任务卡、全局准备清单 | 与用户当前任务竞争 |
| 简化版／进阶版全局切换 | 让导航因模式变化，不能真正分离不同需求 |
| 取号页中的采样、模型、均速和空折线 | 并非完成取号所需信息 |
| 独立于当前号码的重复预测入口 | 让用户在页面间重新选择和输入 |
| 正常未配置状态的常驻警告 | 把可选能力误呈现为故障 |

## 验证方式

以下为拟定验收目标，不是已经测得的改进效果。

| 场景 | 目标 |
| --- | --- |
| 第一次打开 | 用户能在短时间内指出在哪里选店取号，不必先看机制图 |
| 已认证回访 | 不进入设置或新手引导即可选店并确认；不能省略最终业务确认 |
| 已有号码 | 默认能找到当前号码，不因切页重复填写 |
| 只想研究排队规律 | 可直接进入本地分析，全程无需认证或了解取号流程 |
| 取号超时 | 明确「结果待确认」，先查结果，避免盲目重试产生重复操作 |
| 采集未开启或样本不足 | 解释下一步，不显示成系统故障，不伪造预测 |
| 无障碍 | 关键路径验证键盘、焦点、放大、屏幕阅读器和状态播报；不只看截图 |

建议先让少量真实使用者分别尝试这些场景，记录犹豫点、错误入口、重复输入和完成时间。当前没有用户访谈或行为分析数据，不应把设计判断描述成多数用户的实测结论。

## 下一步

先确认「一个应用、两个工作区」的边界，再做三个核心页面的原型：选店、当前号码、本地分析。原型阶段比较三种清晰不同的布局方向，选定后才编写新的规格、计划和实施任务。不要直接在现有大页面上继续叠加组件。

本轮不改业务代码、不重启服务、不影响正在使用的认证与订单。
